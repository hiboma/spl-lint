# CLAUDE.md - spl-lint

## Project Overview

A static analysis tool (linter) for Splunk Search Processing Language (SPL).
It takes query strings as input and detects syntax errors and best practice violations.

- Language: Rust (edition 2024)
- Target: Splunk Search Processing Language (SPL, SPL2)

## Build & Test

```bash
cargo build          # Build
cargo test           # Run all tests
cargo run -- FILE    # Run linter
```

## CLI Usage

```bash
spl-lint <file>...               # Lint files
echo 'query' | spl-lint          # Lint from stdin
spl-lint --format json <file>    # Output in JSON format
spl-lint --disable W002 <file>   # Disable a rule
spl-lint --list-rules            # List all rules
spl-lint --list-commands         # List SPL commands
spl-lint --list-functions        # List eval functions
spl-lint --verbose <file>        # Show message on lint success (-v also works)
spl-lint --trim <file>           # Strip comments and print formatted query
spl-lint --trim --write <file>   # Strip comments and write back to file
spl-lint --spl2 <file>          # Lint in SPL2 mode
spl-lint --spl2 --list-rules    # List SPL2 rules
spl-lint --spl2 --list-commands # List SPL2 commands
spl-lint --spl2 --list-functions # List SPL2 eval functions
```

- Exit code: 1 if errors/warnings found, 0 otherwise
- Text output uses miette for source-span annotated display

## Architecture

The tool is structured in three layers.

```
CLI (main.rs)    -- I/O via clap + miette
Linter           -- Rule trait + LintEngine for AST traversal
Parser           -- Hand-written recursive descent parser (Lexer -> Token -> AST)
```

Data flow: `Source string -> Lexer -> Vec<Token> -> Parser -> AST (Query) -> LintEngine -> Vec<Diagnostic>`

## SPL Syntax Specification (Implemented)

### Tokens Recognized by Lexer

| Category | Tokens |
|---|---|
| Literals | Integer, Float, String (`"..."`), Wildcard |
| Identifiers | Plain (`field`), Dotted (`src_ip.country`) |
| Keywords | `AND`, `OR`, `NOT` (uppercase only), `as`, `by`, `true`, `false` (case-insensitive) |
| Operators | `=`, `!=`, `<`, `<=`, `>`, `>=`, `\|`, `!`, `+`, `-`, `*`, `/`, `%` |
| Delimiters | `()`, `[]`, `,`, `.`, `:` |
| Wildcards | `*foo*`, `error*`, `*` |
| Comments | Backtick (`` `comment` ``) |

### AST Nodes Generated by Parser

- `Query` -- List of pipeline stages
- `PipelineStage` -- `StageKind` (Search / Command)
- `SearchExpr` -- FreeText, FieldFilter, And, Or, Not, Grouped, Wildcard, SubSearch
- `Command` -- Command name + argument list (positional, named, by-clause, as-clause)
- `Expr` -- Number, String, Bool, Field, Wildcard, FunctionCall, BinaryOp, UnaryOp, SubSearch
- `FunctionCall` -- Function name + argument list

### SPL-Specific Notes

- **AND binds tighter than OR**: `a OR b AND c` is interpreted as `a OR (b AND c)`
- **Implicit AND**: `src=a dst=b` is equivalent to `src=a AND dst=b`
- **Keyword case sensitivity**: `AND`, `OR`, `NOT` are keywords only in uppercase
- **`as`, `by` are case-insensitive**: `AS`, `By`, `by` are all recognized as keywords
- **Subsearch**: Written inside `[]`, e.g., `[search ...]`
- **Backtick comments**: `` `this is a comment` `` syntax

## SPL1 Lint Rules

| ID | Severity | Category | Description |
|---|---|---|---|
| `E001` | error | syntax | Syntax error (parse failure) |
| `W001` | warning | performance | Search with only `*` (matches everything) |
| `W002` | warning | correctness | Unknown command name |
| `W003` | warning | correctness | Missing required arguments for command |
| `W004` | info | style | No whitespace around pipe `\|` |
| `W005` | warning | correctness | Ambiguous AND/OR precedence (mixed without parentheses) |
| `W006` | info | performance | Filter after aggregation command |
| `W007` | warning | correctness | Unknown eval function name |

## SPL2 Lint Rules

| ID | Severity | Category | Description |
|---|---|---|---|
| `S001` | error | syntax | SPL2 syntax error (parse failure) |
| `S002` | warning | correctness | Unknown SPL2 command name |
| `S003` | warning | correctness | Unknown SPL2 eval/stats function name |
| `S004` | warning | correctness | String concatenation with `.` (use `+` in SPL2) |
| `S005` | info | style | Special-character field name without single quotes |

## Adding New Rules

1. Create a new file in `src/linter/rules/`
2. Implement the `Rule` trait (`id`, `description`, `check`)
3. Add the module to `src/linter/rules/mod.rs`
4. Register the rule in `LintEngine::new()` in `src/linter/mod.rs`
5. Add tests in `#[cfg(test)]` in `src/linter/mod.rs`

```rust
// Rule trait
pub trait Rule {
    fn id(&self) -> &'static str;
    fn description(&self) -> &'static str;
    fn check(&self, query: &Query, source: &str) -> Vec<Diagnostic>;
}
```

## Coding Conventions

- Files must end with a newline (POSIX compliance)
- Tests are written in `#[cfg(test)] mod tests` within each module
- AST traversal in rules is done recursively (`check_stage` -> `check_search` -> `check_expr`)
- When adding new AST nodes, add matching branches to `check_expr` / `check_search` in all rules
